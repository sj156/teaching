# Write Lecture Notes: computation

Apply these standards within the scope selected in [SKILL.md](../SKILL.md). This reference does not initiate a separate review pass or expand the task.

## Self-contained notes

- Make the lecture notes themselves sufficient to follow every example, illustration, derivation, and computational investigation within the requested scope. Include the necessary setup, data or fully specified data access, parameter values, reasoning, results, and interpretation in the notes. Earlier material in the same notes may be cross-referenced.
- Print small, simple datasets directly in the notes as clearly labeled tables, following the course's existing examples. Include variable definitions, units, sample sizes, and any preprocessing needed to use them. When sufficient statistics replace raw observations, label them as summaries and explain why they suffice under the stated model. Code literals alone should not be the only presentation of a small teaching dataset. For larger datasets, provide an appropriate preview or summary and fully specified access and preparation instructions.
- Make printed datasets compact and readable: use available page width for repeated variable groups, narrow spacing within a group, and wider spacing between groups. Omit observation numbers unless the index has a substantive role. Retain units and consistent alignment. If a table adds no useful information beyond a clear scatterplot, it may be omitted provided exact data or fully specified access remain available.
- Do not require a separate script, repository, or notebook to understand an example. Default to clearly labeled, language-neutral pseudocode in the lecture notes: specify inputs, outputs, mathematical operations, iteration, and accuracy checks without assuming R syntax. Keep data, results, figures, and interpretation in the notes. Use actual code only when language-specific implementation is itself a learning objective or the instructor requests it; label it as runnable code and define its inputs and helpers. Do not present executable-looking fragments as pseudocode.
- Display the relevant figures, tables, and numerical results in the notes and explain what they establish. Internal source assets and authoring scripts may generate them, but must not become a prerequisite for the reader. Do not confuse self-contained exposition with requiring one physical source file.
- Place executable R implementations in one course-wide R Markdown computational companion when requested, organized by the lecture notes' section numbers. The packet may begin with the current section and grow to include earlier sections when revisited and later sections as developed. Match its examples to lecture section numbers; include data, parameter choices, complete code, displayed outputs and plots, accuracy checks, interpretation, and a small extension. Use fixed random seeds and minimal dependencies, and verify rendering from a fresh session. The companion must not replace essential mathematical reasoning, algorithmic steps, illustrations, or conclusions in the notes.
- Keep the lecture notes the primary deliverable. With limited time or budget, revise the requested notes first and add only the current worked example to the companion. Grow the companion incrementally as the course develops; do not proactively migrate unrelated sections or build an elaborate publishing system.
## Computational investigations and practice

- Present core computational procedures once, in numbered algorithm environments using language-neutral pseudocode with explicit inputs, outputs, loops, and sampling or update steps. Do not create a parallel category of prose-only "pseudocode examples" duplicating those algorithms. For LaTeX, reuse the course style's existing algorithm environments. Check available packages before adding compatible environments; do not assume a particular private style package is installed.
- Number algorithms within their subsection: for example, Algorithm 3.3.1, Algorithm 3.3.2, then Algorithm 3.4.1. Configure the counter reset, displayed number, and unique hyperlink anchors in the course style, and use labels and cross-references rather than hard-coded algorithm numbers.
- Accompany algorithms with a nearby schematic or flowchart when the workflow has a meaningful dependency, branch, iteration, or shared quantity to explain. Show the main inputs, stages, dependencies, branches or iteration, and outputs as relevant; for sampling algorithms, make shared quantities and repeated draws clear. Use concise labels and an informative caption, and cross-reference the figure and algorithm in the exposition. The schematic should clarify the flow rather than repeat every line of pseudocode. Reuse or adapt an existing diagram when it already depicts that algorithm accurately.
- Keep master preambles minimal: document class, the course style package (with necessary supported options), and document metadata. Keep reusable layout and numbering policies in the style, and preserve document-specific behavior through explicit options rather than silently changing defaults for other courses.
- When a topic benefits from it, develop a larger integrated computational investigation after the local mechanics have been established. Connect the setup, implementation, diagnostic displays or summaries, interpretation, and limitations to the concepts taught. There may be none, one, or several, depending on pedagogical value.
- Make computational work reproducible in the language and workflow of the course. State the model or input data, parameter choices, simulation setup, and the quantity being assessed. Verify code and reported outputs when execution is available; distinguish actual results from proposed experiments.
